Getting computer vision onto the edge

A model that scores well in a notebook is only half the job. The other half is making it run where the data actually is — on a camera, a drone, or a small board in the field — fast enough and on a power budget that a data-centre GPU never has to worry about. That gap between “it works on my machine” and “it works on the device” is where a lot of the interesting engineering lives.

Why the edge is hard

Edge deployment trades away compute and memory in exchange for low latency, privacy, and independence from a network connection. A detector that comfortably runs at high resolution on a workstation may be far too heavy for an embedded board. The practical questions become: how large is the model, how many milliseconds does one frame take, and how much of that latency the application can actually tolerate.

Techniques that help

Several tools narrow the gap. Quantisation shrinks weights from floating point to lower-precision integers, cutting model size and speeding up inference with a small, measurable accuracy cost. Pruning removes redundant connections. Choosing an architecture designed for efficiency, rather than scaling down a large one, often wins outright. And exporting to a runtime tuned for the target hardware can matter as much as the model itself.

Measure what the user feels

The most useful metric on the edge is rarely a single accuracy number. It is the end-to-end latency a person or a downstream system experiences, measured on the real device under realistic input, not on a benchmark. Reporting accuracy alongside latency and model size gives an honest picture of the trade-off, and it makes it obvious when a small drop in accuracy buys a large gain in responsiveness.

The takeaway

Edge computer vision rewards engineers who care about the unglamorous parts: preprocessing, quantisation, and honest measurement on real hardware. The reward is a system that keeps working when the network does not — which, for most real deployments, is the whole point.
